# Kaffeed

A frontend-only, offline-capable Point of Sale app for a single mobile device,
built for a street-food / coffee stall. Named after Kaffi (the dog) + "feed".

Built with React + Vite + TypeScript, with all data stored locally in the
browser via IndexedDB (Dexie). It installs as a PWA so it launches from the
phone's home screen and the app shell works offline. Prices are in Philippine
pesos (₱).

## Features

- **Menu** — items grouped into categories (Drinks, Snacks, Rice Meals, …),
  each with a base price and an availability ("sold out") toggle. No inventory
  tracking: finished street food is not stock-counted.
- **Modifiers** — items can carry sizes, flavours/variants, and add-ons:
  - single-select groups (e.g. Size, Flavour) behave like radios,
  - multiple-select groups (e.g. Add-ons) behave like checkboxes,
  - required single-select groups must be chosen before adding to the order.
  Each option carries a price delta that is added to the item's base price.
- **Checkout** — category tabs, tap an item to add it (a picker opens for
  customizable items), adjust quantities, see a running total. Identical
  item+modifier combinations stack onto one line; different ones stay separate.
- **Payments** — **Cash** or **GCash via QR**. Choosing GCash shows the stall's
  QR code (`public/gcash-qr.png`) for the customer to scan, then the cashier
  confirms "Payment received" to complete the sale.
- **Receipt** — a print/share-friendly receipt after each sale, listing each
  line's chosen modifiers, unit price, the total, and the payment method.
- **Reports** — daily sales total and transaction count, with a date picker.
- **Offline PWA** — installable, works without a network connection.

All state is managed with focused React Contexts (`MenuContext`, `CartContext`,
`SalesContext`) composed at the app root. Data access is isolated in repository
modules (`menuRepo`, `saleRepo`) that wrap Dexie.

## Requirements

- Node.js 18+ (developed on Node 24).
- A modern browser.

> On Windows PowerShell, if `npm` is blocked by the script execution policy,
> use `npm.cmd` / `npx.cmd` instead of `npm` / `npx`.

## Getting started

```bash
npm install
npm run dev
```

Open the printed local URL in your browser. On first launch the menu is seeded
with a sample coffee / street-food menu.

## Setting the GCash QR code

The app displays `public/gcash-qr.png` on the GCash payment screen. A plain
placeholder image is generated by `scripts/generate-icons.mjs`. To use your real
QR, simply replace that file:

1. Save your GCash QR image as `public/gcash-qr.png` (a square PNG works best).
2. Re-run `npm run build` (or restart `npm run dev`).

No code change is needed as long as the filename stays the same.

## Install on a phone (PWA)

1. Build and serve the production bundle so the service worker is active:
   ```bash
   npm run build
   npm run preview -- --host
   ```
   `--host` exposes the preview server on your local network so the phone can
   reach it at `http://<your-computer-ip>:<port>`.
2. On the phone, open that URL in the browser.
3. Use the browser's **Add to Home Screen** / **Install app** option.
4. Launch "Kaffeed" from the home screen. After the first load, the app shell
   works offline.

## Data & privacy

- There is no backend and no network sync. Everything lives in this device's
  browser storage (IndexedDB, database name `kaffeed-pos`).
- Clearing the browser's site data for this app erases all menu items and sales.

## Project structure

```
src/
  db/            Dexie instance (db.ts) + sample menu seed
  repositories/  Data access (menuRepo, saleRepo) — the only code touching Dexie
  types/         Shared domain types (MenuItem, ModifierGroup, Sale, PaymentType)
  context/       MenuContext, CartContext, SalesContext
  pages/         Checkout, Menu, Receipt, Reports
  components/    Layout, ErrorBoundary
  utils/         money (PHP) + date helpers
```

## Extending

- **More payment types:** `PaymentType` is an enum (`CASH`, `GCASH`) and every
  sale stores a `paymentType`. Add new enum members and a selector on checkout —
  no schema migration required for the field itself.
- **Modifier editing UI:** new items are created with name/category/base price;
  modifier groups are currently defined in the seed data. A richer modifier
  editor on the Menu page would be the natural next step.
- **Schema changes:** bump the Dexie version in `src/db/db.ts` with a new
  `.version(n).stores(...)` block; never edit a shipped version block. The app
  is already on v2 (grocery `products` → street-food `menuItems`).
```



## Deployments & branches

This repository feeds **two independent Vercel deployments from the same repo**.
They run different generations of the app and must never be mixed:

| Deployment        | Branch     | What it is                                             | Env vars                                              |
| ----------------- | ---------- | ------------------------------------------------------ | ----------------------------------------------------- |
| **Client (KainNa)** | `master` | The original single-stall, offline-only POS (old app). | none                                                  |
| **Global (SaaS)**   | `KainNa` | The multi-tenant, cloud + offline platform (Phase 1+). | `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`         |

Two separate Vercel **projects** both import this repo:

- **Client project** → Production Branch `master`; no Supabase env vars; client's
  own domain. Runs fully offline-local — no sign-in, no cloud.
- **Global project** → Production Branch `KainNa`; Supabase env vars set; global
  domain. Runs full multi-tenant cloud sync.

Vercel inlines `VITE_*` vars at **build time**, so each project bakes in its own
configuration when it builds its branch. The global app degrades gracefully to
local-only if its Supabase vars are ever missing (see `src/config/supabase.ts`).

> **Critical rule: never merge `KainNa` into `master`.** The client's production
> deployment builds from `master`. Merging the global/Phase-1 work into `master`
> would push the entire store migration and cloud code onto the live client
> unintentionally. Keep global work on `KainNa` (or a dedicated global production
> branch); promote to the client only by deliberate, reviewed changes to the old
> app on `master`.

### Secrets

`.env` and `knowledge/supabase-creds.json` are gitignored and must never be
committed. The Supabase **anon** key is safe to expose in the client bundle
(Row-Level Security protects tenant data); the **service_role** key must never
appear in client code, env `VITE_*` vars, or the repo.

### Before a production launch of the global app

- Re-enable **Confirm email** in Supabase Auth (it was disabled during testing).
- Set the Supabase env vars in the global Vercel project.
